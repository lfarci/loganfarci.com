# Internationalization (Multilanguage)

[Back to the specs index.](./README.md)

Support for the site in **more than one language**. This is a **planned** capability —
today the site is English-only — so most of this spec describes direction, not current
behavior. It exists so that when i18n lands it fits the site's model and principles
instead of bolting on a heavy framework. See
[vision.md](./vision.md#accessibility-ambitions) for the "why".

## Current state

- The document is statically `<html lang="en">` and `og:locale` is `en_US`.
- All UI strings and content are English, authored inline.
- There is **no** i18n framework, message catalog, or locale routing yet.

## Target languages

The site should be available in **English**, **French**, and **Dutch** for now:

| Locale | Language | `lang` / `og:locale` |
| --- | --- | --- |
| `en` | English (default, canonical source) | `en` / `en_US` |
| `fr` | French | `fr` / `fr_FR` |
| `nl` | Dutch | `nl` / `nl_NL` |

English is the default and source language; French and Dutch are additive translations.
The set is intentionally small and left-to-right, so no RTL work is needed yet. Adding a
locale later means extending this list and the machinery below, not redesigning it.

## Principles

- **Keep it simple, don't reinvent the wheel.** Prefer a small, well-established i18n
  helper or plain message catalogs over a heavy runtime framework. Only add weight a
  real second language justifies (see [non-goals.md](./non-goals.md)).
- **Stay static.** Every locale **MUST** remain **statically prerendered** — one HTML
  file per route per locale. i18n must not introduce a runtime translation server or
  client-only content (see [architecture.md](./architecture.md#ssr--prerender-contract)).
- **English stays canonical.** English is the source language; other locales are
  additive translations, never a fork of the content.

## Planned approach

### URL and locale scheme

- Use a simple, conventional **path prefix** per locale. English (default) stays
  unprefixed at `/`, with `/fr/...` for French and `/nl/...` for Dutch. Keep the
  structure flat and predictable; slugs stay kebab-case.
- Apply the default-locale convention (English unprefixed) consistently across every
  route.

### Prerendering

- Extend `getStaticRoutes()` (see
  [architecture.md](./architecture.md#routes-and-page-responsibilities)) to enumerate
  **locale x route**, so the prerender step writes a static page for each.
- Each prerendered document **MUST** set the correct `lang` and `og:locale`.

### Content and strings

- **UI strings:** move user-facing text into a per-locale **message catalog** (e.g.
  JSON keyed by locale) resolved at build time — no hardcoded strings in components.
- **Articles:** translated markdown lives alongside the source (for example a
  locale-suffixed file such as `content/articles/{slug}.{locale}.md`), following the
  existing content pipeline. A missing translation **SHOULD** fall back to English
  rather than 404.
- **Structured data:** translatable fields in `content/data/*.json` need a per-locale
  strategy that keeps the [data contracts](./data-contracts.md) intact.

### SEO and discoverability

- Emit `hreflang` alternate links between locale variants, plus a per-page canonical.
- Include **every** locale variant in `sitemap.xml`.
- Keep `llms.txt` / `llms-full.txt` correct across locales (see
  [accessibility.md](./accessibility.md#machine-readers-and-llms)).

### UI

- Provide a **language switcher** that preserves the current page across locales and
  remembers the choice.
- Optionally use the browser's `Accept-Language` for a first-visit suggestion, done in a
  way that does not break static delivery.

### Right-to-left

- Only relevant if an RTL language is added; if so, drive direction from the document
  `dir` and logical CSS properties. Not planned until such a language is on the roadmap.

## Rules for agents

- Do not hardcode new user-facing strings in a way that blocks translation; assume text
  may need a catalog key.
- Any i18n work **MUST** keep every locale statically prerendered and **MUST NOT**
  introduce a runtime translation service.
- When adding a locale, update prerendering, `hreflang`, the sitemap, and the machine
  files together so discovery stays complete.
- Prefer extending the existing content pipeline and Tailwind/theme setup over adding a
  parallel system.
